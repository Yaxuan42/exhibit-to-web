如何用 Claude Code 半天搭起这个博客 How I Built This Blog in Half a Day with Claude Code

Brief → Design → Build → Deploy，一次元叙事的记录。 A meta-narrative: the first post is the making of the site itself.

2026 · 04 · 18 · 约 1500 字 ~ 6 min read

这个博客的第一篇文章，内容就是搭建它本身。这不是偷懒——一个刚刚诞生的空间最诚实的样本，恰恰是它从无到有的过程。

起点是一个叫 exhibit-to-web 的 Claude Code skill，本来是给展览做线上化的。它提出一个四阶段方法——Brief → Design → Build → Deploy。我把它借来做个人博客，发现这套流程一样成立。

第一阶段 · Brief

我没让它立刻动手写代码。Claude 先问了我一串问题：你是谁、网站主用途、语言、板块、有没有素材、有没有美学参考。看起来像废话，但一个没经过 Brief 就动工的项目，八成会在第三天推翻重来。

我给出的回答很短：

产品负责人、vibeCoder。
个人博客为主，博客不一定都是文字版本。
主要是中文，但可以英文切换。
初期主要是文章。
暂时没有素材，可以参考当前站点。

关键在最后一句。它让后续所有的美学决策都有了方向——参考原项目那种"白盒子画廊"感，克制、书卷气、可读。

第二阶段 · Design

这一阶段它没有直接出代码，而是给我一份 Design Brief——字体、色板、间距、语气、反参考，一次性摆清楚。这种"决策先行"的做法有个好处：代码只是 Brief 的翻译，翻译没写好不怪译者，要改就改 Brief。

最终选定的 tokens：

字体Noto Serif SC（中）/ Fraunces（英）/ JetBrains Mono（等宽）
背景#FAF8F3 暖米白
文字三级灰 #1A1A1A / #4A4A4A / #6E6E6E
Accent#8B3A2F 低饱和朱砂
基准间距8px，行高 1.85–1.9
Tone克制、温暖、可读

然后是 反参考——深色加渐变、卡片阴影、SaaS landing page、emoji 装饰——任何一样出现，博客就会立刻塌缩成模板站。

第三阶段 · Build

写代码这部分反而是最轻的。严格遵循原项目的"单文件 HTML + 零依赖"原则：

  • index.html — 首页：题记 + 文章列表 + 语言切换
  • posts/*.html — 每篇文章一个独立 HTML，便于 SEO 与独立分享
  • about.html — 关于，先留占位
  • 没有 npm、没有构建、没有框架。Google Fonts 是唯一的外部依赖

语言切换用 localStorage 记住选择，CSS 里用 [data-lang] 控制显隐。这里有个关键决定：不是两个站点，是一个站点的两套内容。这样路由、书签、分享链接都不会出问题。

html[data-lang="zh"] [lang="en"]:not(.bilingual) { display: none; }
html[data-lang="en"] [lang="zh"]:not(.bilingual) { display: none; }

想让某个元素在两种语言下都显示？加 .bilingual。

第四阶段 · Deploy

推到 GitHub，连上 Vercel，git push 即上线。域名备案这一步之后再补——国际域名配 Cloudflare DNS 先顶上。

最让我意外的地方

原项目是为展览设计的，核心假设是"一个有物理空间的短暂事件，需要被数字化保存"。个人博客的假设完全不同——它没有截止日期，内容是持续生长的。

但 Brief → Design → Build → Deploy 这套流程，在两种场景下同样奏效。原因可能在于：任何"把想法变成可见之物"的工作，本质上都有一个理解 → 确立 → 实现 → 让它被访问到的结构。展览和博客只是同一个结构的不同外壳。

这正是我想要的第一篇文章：梯子搭到一半，正在往上走，顺手把脚下的每一阶拍下来。

这篇文章与 Claude Code 共同写就。你正在看的站点就是它生产的副产物。

The first post on this blog is about building the blog itself. Not laziness — the most honest sample from a newborn space is the record of its coming into being.

The starting point was a Claude Code skill called exhibit-to-web, originally built for digitizing physical exhibitions. It proposes a four-phase workflow — Brief → Design → Build → Deploy — which, it turns out, works just as well for a personal blog.

Phase 1 · Brief

I didn’t let it write code immediately. Claude first asked me a list of questions: who are you, what’s the site for, what languages, what sections, what materials do you have, any aesthetic references. These feel like overhead — until you’ve shipped a project that skipped the Brief and had to be rebuilt in week two.

My answers were short:

Product lead, vibeCoder.
Personal blog, mostly but not only text.
Chinese primary, with an English toggle.
Articles only, to start.
No materials yet — reference the current site.

The last line was the key. It gave every downstream aesthetic decision a direction: that same "white-cube gallery" feel — restrained, literary, legible.

Phase 2 · Design

Instead of jumping into code, Claude produced a Design Brief — fonts, palette, spacing, tone, anti-references. Decisions-first has one advantage: code becomes a translation of the Brief. If the result is wrong, fix the Brief, not the code.

The tokens we landed on:

TypefacesNoto Serif SC (Chinese) / Fraunces (English) / JetBrains Mono (metadata)
Background#FAF8F3 warm off-white
Ink#1A1A1A / #4A4A4A / #6E6E6E
Accent#8B3A2F low-saturation cinnabar
Base unit8px, line-height 1.85–1.9
Tonerestrained, warm, legible

And the anti-references: dark backgrounds with gradients, card shadows, SaaS landing pages, emoji decoration. Let any of that "AI slop" in and the blog becomes a template overnight.

Phase 3 · Build

Writing the code was the easy part. Strict single-file HTML, zero dependencies:

  • index.html — hero, epigraph, article list, language toggle
  • posts/*.html — one standalone HTML per post, good for SEO and sharing
  • about.html — placeholder for now
  • No npm, no build, no framework. Google Fonts is the only external dependency.

Language switching uses localStorage to remember the choice, and CSS driven by a [data-lang] attribute on <html>. One key decision: it’s not two sites, it’s one site with two language tracks. Routing, bookmarks, and shared links all keep working.

html[data-lang="zh"] [lang="en"]:not(.bilingual) { display: none; }
html[data-lang="en"] [lang="zh"]:not(.bilingual) { display: none; }

Want an element visible in both? Add .bilingual.

Phase 4 · Deploy

Push to GitHub, connect to Vercel, live on git push. Domain and ICP filing can come later — an international domain plus Cloudflare DNS is enough for day one.

What surprised me

The original skill was built for exhibitions. Its core assumption is "a time-limited physical event needs a digital afterlife." A personal blog is the opposite — no deadline, continuously growing content.

Yet Brief → Design → Build → Deploy works in both cases. The reason, I think, is that any work of turning an idea into something visible shares the same underlying structure: understand, decide, implement, make it reachable. Exhibitions and blogs are different shells over the same skeleton.

Which is exactly the first post I wanted: the ladder half-built, still climbing, photographing each rung on the way up.

This post was written collaboratively with Claude Code itself. The site you’re looking at is the artifact.
